# E2E テスト整備 仕様書

## 概要

Kan. Sheets BI の品質を自動検証するため、Playwright を用いた E2E テストスイートを整備する。
対象は `docs/bi-tool-spec.md` §13 が定める主要フロー・セキュリティ・PDF・ウィジェット操作の各シナリオで、実際のブラウザ操作を通じてアプリケーション全体が仕様どおりに動作することを確認する。
テストは外部サービス（Google、Upstash）に接続せず、E2E 専用 DB とフェッチスタブを用いてローカルおよび開発環境で安定して実行できることを要件とする。

### 前提・制約

以下はオーケストレーターが決定した前提であり、仕様全体に通底する。

| 項目 | 決定内容 |
|------|----------|
| 認証 | Google OAuth の実ログインは自動化しない。`AUTH_SECRET` で署名した Auth.js JWT セッション Cookie をブラウザに直接注入してログイン状態を作る。ログインページの表示確認は実画面で行う。 |
| DB | 実 PostgreSQL（E2E 専用 DB）。`DATABASE_URL` を専用 DB に向け、各テスト前後でマイグレーション適用・テストデータ投入・後始末を行う。 |
| Google Sheets | 本番コードを変えずに、E2E 実行時のみ Node プロセスの `fetch` をスタブして固定 CSV を返す（実 Google サービスに接続しない）。 |
| Upstash Redis | E2E では接続しない。キャッシュが必要な場合はスタブまたはインメモリ代替を使う。 |
| 実行 | `pnpm e2e` 1コマンドで「アプリ起動 → テスト実行 → 後始末」まで完結する。通常の `pnpm vitest run` には含めない。 |
| CI | 未整備のため対象外。実行手順は本仕様書末尾に記載する。 |

## 機能一覧

### FEAT-E2E-001: テスト環境基盤（セッション注入・フェッチスタブ・DB 前後処理）

- **優先度**: Must
- **説明**: 全テストシナリオが依存する共通基盤を確立する。具体的には「Auth.js セッション Cookie の生成とブラウザへの注入」「Google Sheets へのリクエストを固定 CSV で返すサーバー側フェッチスタブの有効化」「テストごとの DB 初期化・テストユーザー/データソース/ダッシュボードの生成と後始末」の3点を含む。この基盤なしでは他のテストシナリオが正しい前提条件を確保できない。
- **受け入れ基準**:
  - [ ] 任意のテストから「ユーザー A のセッション Cookie を持つブラウザコンテキスト」を取得できるヘルパーが存在し、そのブラウザで `/dashboards` にアクセスするとログイン済み状態として扱われる
  - [ ] テスト実行中に Google の `docs.google.com` および `sheets.googleapis.com` への実ネットワーク接続が発生しない（ネットワーク監視で確認可能）
  - [ ] フェッチスタブが返す固定 CSV はヘッダー行＋最低 3 行のデータを含み、数値列・文字列列・日付列を各 1 列以上持つ
  - [ ] 各テストスペックの `beforeEach` / `afterEach` でテスト用レコードが投入・削除され、テスト間でデータが漏洩しない
  - [ ] E2E 専用環境変数（`DATABASE_URL` / `AUTH_SECRET` / `AUTH_URL` の E2E 値）を `.env.e2e` で管理でき、`pnpm e2e` 実行時にそれを読み込む

### FEAT-E2E-002: 未認証アクセスのリダイレクト検証

- **優先度**: Must
- **説明**: セッション Cookie を持たないブラウザが保護ページにアクセスしたとき、ミドルウェアが `/login` へリダイレクトすることを検証する。対象ページは `/dashboards`、`/datasources`、`/settings` の 3 パス。これはセキュリティ仕様（§7, §FR-6）の最初の防衛線であり、誤って除外されていないことを継続確認する。
- **受け入れ基準**:
  - [ ] Cookie なしで `/dashboards` にアクセスすると最終的に `/login` に到達し、ログイン UI が表示される
  - [ ] Cookie なしで `/datasources` にアクセスすると最終的に `/login` に到達する
  - [ ] Cookie なしで `/settings` にアクセスすると最終的に `/login` に到達する
  - [ ] リダイレクト後の URL または画面に「ログイン」に相当する UI 要素が存在する
  - [ ] 有効なセッション Cookie を持つブラウザでは同じパスにアクセスしてもリダイレクトされない

### FEAT-E2E-003: 主要フロー（ログイン→データソース登録→チャート作成→レイアウト保存→PDF 出力）

- **優先度**: Must
- **説明**: §13 が定める中核シナリオ。ユーザーがセッション注入でログイン済み状態から開始し、データソース登録・チャートウィジェット作成・レイアウト保存・PDF ダウンロードまでの一連のステップをエラーなく完遂できることを確認する。各ステップは前のステップの成果物を使うため、途中でエラーが発生した場合はそこで停止して記録する。
- **受け入れ基準**:
  - [ ] セッション注入後に `/dashboards` を開くとダッシュボード一覧が表示される
  - [ ] 「新規ダッシュボード作成」操作でダッシュボードが作成され、編集画面に遷移する
  - [ ] データソース登録 UI でスプレッドシート URL と range を入力して登録すると、フェッチスタブが返す固定 CSV のプレビューが表示される
  - [ ] 「ウィジェットを追加」操作でチャート種別・タイトル・データソースを選択してウィジェットが作成され、グリッドに表示される
  - [ ] ウィジェットを編集モードでドラッグまたはリサイズすると、レイアウトが自動保存される（デバウンス後に `PUT /api/dashboards/:id/layout` が成功する）。ページをリロードしても、同じウィジェットが変更後の位置・サイズで表示される
  - [ ] 「PDF 出力」ボタンを押すと PDF ファイルのダウンロードが開始される
  - [ ] ダウンロードされたファイルのバイト列が `%PDF` で始まる（有効な PDF ファイル形式）

### FEAT-E2E-004: PDF トークンの有効性と単回使用

- **優先度**: Must
- **説明**: PDF 出力で使われるトークンが仕様（§5 FR-5, §7, §7a）どおり単回使用であることを検証する。同一トークンで印刷ルートに 2 回アクセスした場合、2 回目はエラー（4xx）になる必要がある。また、PDF そのものが有効な形式であることも確認する。
- **受け入れ基準**:
  - [ ] `GET /api/dashboards/:id/pdf`（または対応する PDF 発行 API）が呼ばれると、`x-pdf-token` ヘッダーを付けた `/dashboards/:id/print` へのアクセスでページコンテンツ（HTML）が返る
  - [ ] 同じトークンを用いて `/dashboards/:id/print` に 2 回目のアクセスを行うと、200 ではなく 4xx（400/401/403/404 のいずれか）が返る
  - [ ] トークンを一切付けずに `/dashboards/:id/print` にアクセスすると 4xx が返る
  - [ ] 最終的にダウンロードされる PDF ファイルのバイト列が `%PDF` で始まる

### FEAT-E2E-005: 所有権保護（他ユーザーのリソースへのアクセス拒否）

- **優先度**: Must
- **説明**: ログイン済みのユーザー A が、別のユーザー B のダッシュボード・データソースにアクセスしようとしたとき、403 または 404 が返ることを検証する。これは §5 FR-6 / §7 / §15 で定める「所有者スコープ」の中核保証であり、Route Handler / Server Action 側の認可ロジックが正しく機能していることを確認する。
- **受け入れ基準**:
  - [ ] ユーザー A のセッションで、ユーザー B のダッシュボード詳細ページ（`/dashboards/:id`）にアクセスすると 403 または 404 に相当するエラー画面が表示される（正常なダッシュボード内容が表示されない）
  - [ ] ユーザー A のセッションで、ユーザー B のダッシュボード PDF API（`/api/dashboards/:id/pdf`）にアクセスすると 403 または 404 が返る
  - [ ] ユーザー A のセッションで、ユーザー B のデータソース API（`GET /api/datasources/:id`）にアクセスすると 403 または 404 が返る

### FEAT-E2E-006: ウィジェット連続追加（2 回目以降が正常に機能する）

- **優先度**: Must
- **説明**: 過去に確認された「2 回目以降のウィジェット追加ができないバグ」（FEAT-BF-004 対応済み）のリグレッションを防止する。1 回目の追加成功後にダイアログを閉じ、再度開いて 2 回目の追加を行っても正常に完了することを自動検証する。
- **受け入れ基準**:
  - [ ] 1 回目の「ウィジェットを追加」操作が成功し、ダッシュボードにウィジェット（widget-1）が表示される
  - [ ] ダイアログを閉じた後、「ウィジェットを追加」ボタンを再度クリックするとダイアログが開き、前回の成功状態がリセットされた空フォームが表示される
  - [ ] 2 回目の追加操作が正常に完了し、ダッシュボードにウィジェット（widget-2）が追加されて計 2 件になる
  - [ ] 3 回目の追加操作も同様に正常に完了し、計 3 件になる

### FEAT-E2E-007: データ取得失敗ウィジェットの分離表示

- **優先度**: Should
- **説明**: データ取得が失敗したウィジェットが他ウィジェットに影響を与えないことを検証する。フェッチスタブで特定のデータソースに対してエラーを返すよう設定し、そのデータソースを使うウィジェットのみエラー表示になり、別のデータソースを使う正常なウィジェットは正常に表示され続けることを確認する。
- **受け入れ基準**:
  - [ ] データ取得失敗に設定されたデータソースを使うウィジェットのカードに、エラーを示す UI 要素（テキスト・アイコン等）が表示される
  - [ ] 同じページの別ウィジェット（正常なデータソース使用）はグラフまたはデータを正常表示している
  - [ ] REAUTH_REQUIRED エラーのウィジェットカードに、データソース設定ページへのリンクに相当する UI 要素が表示される
  - [ ] ページ全体が JavaScript エラーでクラッシュしない（コンソールに未処理エラーが出ない）

### FEAT-E2E-008: `pnpm e2e` による単一コマンド実行

- **優先度**: Should
- **説明**: 開発者が `pnpm e2e` の 1 コマンドで「E2E 用アプリ起動 → 全テスト実行 → 後始末」を完結できることを要件として定める。このコマンドは通常の `pnpm vitest run` とは独立しており、vitest の `include` 設定（`src/**/*.test.*`）に影響しない。実行手順と環境変数の設定方法を本仕様書末尾で説明する。
- **受け入れ基準**:
  - [ ] `pnpm e2e` の実行で E2E テスト用アプリが別ポートで起動し、全テストが実行されてから終了する
  - [ ] `pnpm vitest run` には E2E テストファイルが含まれない（vitest 設定の `include` が `src/**/*.test.*` のまま）
  - [ ] テスト終了後（成功・失敗どちらでも）にアプリプロセスが終了する
  - [ ] 失敗したテストの名前と失敗理由がターミナルに表示される

## UXフロー（検証対象のユーザー体験）

### 主要フロー

1. テストが Auth.js JWT Cookie をブラウザに注入し、ログイン済み状態を作る
2. `/dashboards` を開き、ダッシュボード一覧が表示されることを確認する
3. 「新規作成」操作でダッシュボードを作り、編集画面に遷移する
4. 「データソースを追加」UI でスプレッドシート URL と range を入力し登録する
5. フェッチスタブが固定 CSV を返し、プレビューテーブルに行データが表示される
6. 「ウィジェットを追加」でチャート種別・タイトル・先ほどのデータソースを選択して追加する
7. グリッドにウィジェットが表示されることを確認する
8. 編集モードでウィジェットを移動またはリサイズし、自動保存の完了後にページをリロードして、変更後の位置・サイズが残ることを確認する
9. 「PDF 出力」ボタンを押し、ダウンロードされたファイルが有効な PDF であることを確認する

### 未認証リダイレクトフロー

1. Cookie を持たないブラウザで保護ページ（`/dashboards` 等）にアクセスする
2. ミドルウェアが `/login` へリダイレクトする
3. ログイン UI が表示されていることを確認する

### 所有権保護フロー

1. テストがユーザー A と ユーザー B のセッションを別々のコンテキストで準備する
2. ユーザー A のコンテキストで ユーザー B のダッシュボード URL に直接アクセスする
3. 403 または 404 に相当するエラーが返り、ダッシュボード内容が表示されないことを確認する

### PDF トークン単回使用フロー

1. ユーザーが「PDF 出力」操作でトークン発行 API を呼ぶ
2. 発行されたトークンを `x-pdf-token` ヘッダーに付けて印刷ルートに 1 回目アクセスする（成功）
3. 同じトークンで印刷ルートに 2 回目アクセスする（4xx が返ることを確認）

### ウィジェット連続追加フロー

1. 「ウィジェットを追加」ボタンをクリックし、1 回目の追加を完了する
2. ダイアログが閉じ、グリッドにウィジェットが 1 件表示される
3. 再度「ウィジェットを追加」ボタンをクリックし、空フォームのダイアログが開くことを確認する
4. 2 回目の追加を完了し、2 件になることを確認する
5. 3 回目も同様に完了し、3 件になることを確認する

## 非機能要件

- **信頼性**: テスト間でデータが漏洩しないよう、各テストの前後で DB レコードを確実にクリーンアップする。フェッチスタブは固定データを返すため、外部サービスの不安定性に影響されない。
- **セキュリティ**: E2E テスト用の `AUTH_SECRET` は本番と異なる値を使い、`.env.e2e` はリポジトリに含めない（`.gitignore` 対象。既存の `.env*` 除外に含まれる）。サンプルとして `.env.e2e.example` を用意し、`.gitignore` に `!.env.e2e.example` を追加してコミット対象にする。テスト用の JWT Cookie は有効期限を短く設定する。
- **パフォーマンス**: 各テストのタイムアウトは 30 秒を上限とする。PDF 生成待ちは `window.__chartsReady` フラグによる 15 秒タイムアウトを引き継ぐ。テストスイート全体の実行時間は 5 分以内を目安とする。
- **独立性**: E2E テストは `pnpm vitest run` のスコープ外に置く。`vitest.config.ts` の `include` は `src/**/*.test.*` のまま変更しない。E2E 設定ファイルは独立したコンフィグ（例: `playwright.config.ts`）で管理する。
- **外部接続遮断**: テスト実行中に Google（`docs.google.com`、`sheets.googleapis.com`）および Upstash への実接続が発生しないことをネットワーク監視で保証する。

## 実行手順

### 前提

- Node.js（プロジェクト規定バージョン）と pnpm がインストールされていること
- E2E 専用 PostgreSQL DB が用意されていること
- `.env.e2e` を以下の変数を埋めて作成すること（`.gitignore` に追加すること）:

```
DATABASE_URL=<E2E専用DB接続文字列>
AUTH_SECRET=<E2E用秘密鍵（本番とは別の値）>
AUTH_URL=http://localhost:3001
AUTH_GOOGLE_ID=dummy
AUTH_GOOGLE_SECRET=dummy
```

### 実行

```bash
# E2E テストの全シナリオを実行する
pnpm e2e
```

このコマンドは内部で以下を順に実行する:

1. `.env.e2e` の環境変数を読み込む
2. E2E 専用 DB にマイグレーションを適用する
3. アプリを別ポート（`AUTH_URL` 指定のポート）で起動する
4. Playwright テストを実行する
5. アプリプロセスを終了する

### 通常テストとの分離確認

```bash
# 単体・結合テスト（E2E を含まない）
pnpm vitest run
```

`pnpm vitest run` の出力に E2E テストファイルが含まれないことを確認する。
