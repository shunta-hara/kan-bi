bi-tool-spec.md（技術仕様書）に書かれた実装詳細（OAuthトークンのリフレッシュ、PDFトークンのjti単回使用、Redisキャッシュのsingle-flightなど）は、機能仕様書ではユーザー・システムが観測できる挙動の文章に翻訳して受け入れ基準に落とし込む。

**Why**: プランナーの原則は「何を作るかだけを定義し、どう作るかは書かない」。しかし bi-tool-spec.md にはレビュー対応として重要な非機能要求（指摘I, 2-1, 3-4 など）が実装方式として書かれているため、それをそのまま転記すると実装詳細の流出になる。一方で完全に無視すると技術仕様との整合が取れなくなる。

**How to apply**: 例えば「PDFトークンは単回使用(jti)・短命・{userId,dashboardId}束縛・ヘッダ渡し」は「PDF出力用のアクセス情報は使い回しできず、短時間で無効になる」と翻訳する。「OAuthリフレッシュトークンの自動更新・revoke検知」は「ログインから時間が経っても裏側でアクセスが維持され、失効時は再認可導線が出る」と翻訳する。次回 web-bi の仕様書を改訂・追加する際もこの変換パターンを踏襲する。[[project-kan-sheets-bi]]
